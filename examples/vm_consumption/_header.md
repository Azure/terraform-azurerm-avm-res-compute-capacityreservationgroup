# VM consumption E2E example

An executable scenario for manual reproduction, temporarily excluded from automated E2E deployment by `.e2eignore`: one reservation and one matching Linux VM. The VM owner is the official [Azure Virtual Machine AVM](https://registry.terraform.io/modules/Azure/avm-res-compute-virtualmachine/azurerm/0.22.0), pinned to exact Registry version **0.22.0**, released 2026-11-16 (tag commit `bac606921999710f478197474ed077c145e8c066`). Its implementation and this example's support resources use AzAPI. Its effective Terraform minimum is **1.16**, with additional random/time/tls provider requirements; installing TLS does not generate a private key. This example explicitly opts in by default with `capacity_reservation_enabled = true`. The reusable reservation module never owns VM associations.

This revised fresh consumer is **not automatic state-migration guidance for an already applied earlier handwritten VM example**. The released-group upgrade fixture starts with this upstream VM owner in its baseline and keeps that owner/address/source unchanged while testing only the group upgrade.

## Approval, eligibility and cost

**Do not apply without separate Azure scope/cost/cleanup approval.** Authenticate with Azure CLI or supported `ARM_*`/OIDC configuration and choose an isolated `resource_group_name`. The selected subscription must already have the required providers registered. No registrations are performed.

The VM and reservation share `vm_size`, `location` and `zone`; the group envelope contains that same zone. Defaults select `Standard_D2s_v5`, zone `1`, and the Canonical `0001-com-ubuntu-server-jammy:22_04-lts-gen2:latest` x64 Gen2 image with Trusted Launch. Verify image availability, `CapacityReservationSupported`, Targeted capacity support, Trusted Launch eligibility, subscription restrictions, regional/VM-family quota and available capacity in the approved region/zone. The example is not a runtime eligibility lookup and does not guarantee current capacity. Configure a compatible approved SKU rather than assuming every SKU works.

One reserved VM slot is billed even when unused. The VM also incurs Premium LRS OS-disk and applicable compute charges; capacity-reservation allocation avoids double charging the matching consumed reservation, not all VM costs. Premium storage satisfies the managed resiliency policy without a policy exception. Disabling association does **not** release the reservation or stop its billing.

## Authentication and exposure

Password authentication is disabled. Supply a real `ssh_public_key` if access is needed. With null (the noninteractive default), Azure's `sshPublicKeys/generateKeyPair` POST creates a genuine 3072-bit RSA pair. Only `publicKey` is exported by the AzAPI action; the returned private key is discarded, never an output or committed credential. This intentionally creates no usable operator login credential. Do not enable HTTP/debug logging that could capture the raw secret-bearing action response; protect state and plan artifacts regardless. Upstream VM credential generation is explicitly disabled, with the supplied/generated **public** key passed through `account_credentials`; no TLS private-key resource is instantiated.

The VM has no public IP, no default outbound Internet access, and an NSG explicitly denying all inbound traffic. Secure boot and vTPM are enabled; the pinned upstream module's disabled boot-diagnostics default is retained. This is an allocation/lifecycle test, not a guest connectivity or application test.

## Ownership, opt-out and teardown

The **upstream VM module** is the sole VM and NIC owner. Its `capacity_reservation_group_resource_id` receives this group's **`resource_id` directly**, without casing transforms, readback-derived inputs or added ignores. It never uses a child ARM ID or the platform `reservationId`. An explicit module dependency waits for the reservation, not merely its container. The reverse dependency keeps the reservation until VM deletion completes; the inspected upstream implementation sets the created OS disk's `deleteOption = "Delete"` and Terraform separately deletes the module-owned NIC/network.

For a **fresh unassociated VM**, set `capacity_reservation_enabled = false` and acknowledge the association decision with `association_change_approved = true`. This passes null to the upstream VM input; that pinned implementation configures **`properties.capacityReservation = null`**. This differs from the earlier handwritten fixture's nested `id = null`; actual clearing and refreshed convergence must be tested, not inferred. For an **already allocated VM**, do not simply flip the switch and assume an in-place update works:

1. With separately approved scope, deallocate the VM and wait for completion; then apply `capacity_reservation_enabled = false` and `association_change_approved = true`, verify an independent VM readback and two normal refreshed plans, and optionally restart it.
2. Alternatively, first apply `reservation_capacity = 0` while association remains enabled, verify the reservation readback, then disable association in a **second** apply. This relinquishes guaranteed capacity and can affect every VM sharing that reservation.
3. Full `terraform destroy` deletes the VM first; Azure removes its association after deletion. Allocation projection latency can still affect reservation deletion and must be investigated, not hidden by broad cleanup.

No updater, second VM writer, deallocation action or subscription mutation runs automatically. Changing name/size/zone requires deliberate migration/replacement planning. Do not remove the module dependency or reservation independently while the VM is associated.

The acknowledgement prevents an accidental opt-out but cannot inspect Azure power state. The staged migration harness checks actual deallocation separately, keeps this VM-owned relationship configured in both released and candidate stages, and treats disassociation as a candidate-only operation. Cross-subscription sharing is **not** VM association coverage: it is MCAPS manual-only and is deliberately absent from single-subscription AVM E2E.

## Managed checks

`avm test e2e --list` excludes `vm_consumption` while `.e2eignore` is present. This user-approved exception records the known upstream association-ID casing drift; it does not convert the failed idempotency checks into passes. Unit coverage and the opt-in manual migration fixture remain available, and configured IDs are unchanged. Remove the marker after the upstream behavior is resolved and an approved live run verifies deployment, two refreshed no-ops and normal cleanup.

Defaults require no interactive credential variable or placeholder value, so policy-plan discovery remains noninteractive. Local mock/validate/policy results do **not** establish deployed E2E, persistence, toggle or teardown success. The separate staged migration fixture pins the same VM Registry source/version independently of the group phase; only the group source changes when an upgrade is reached.

**Historical upstream observation (2026-11-10, unreleased VM commit `0bd2e266b1676c77ccb69f071d83c7161d12945c`, not a 0.22.0 live result):** an actually applied Registry v0.2.0 group baseline passed independent Azure association/identity/disk/NIC readbacks, but **two normal refreshed plans** each proposed one VM update caused only by group-association ARM-ID casing. Neither update was applied. No casing transform, readback-derived input, added ignore or upstream patch was used. The group candidate upgrade and live deallocation/disassociation/reassociation phases were therefore **not reached**. The earlier handwritten VM fixture reproduced the same behavior and remains separate failed evidence, not an upgrade pass. This is an upstream follow-up, not a blocker attributed to the group refactor.

Release 0.22.0 preserves the old pin's VM association interface, null opt-out body, defaults, outputs and provider constraints; its runtime change is the interfaces utility selection **0.9.0 → 0.10.0**. That utility makes location optional when telemetry is disabled and fixes a null-safe customer-managed-key validation; this fixture supplies location and configures no customer-managed key. No association-casing fix is claimed.

**Released VM 0.22.0 live result (2026-11-16):** a separately approved isolated run successfully applied the released group v0.2.0 baseline with this VM version and verified independent group/child/VM identities, reservation properties, disk/NIC and association/backlink readbacks. Both normal refreshed plans reproduced only the same VM association-ID casing update; neither was applied and **zero of two plans were no-ops**. The group candidate upgrade and deallocation/disassociation/reassociation phases were **not executed**. This remains an upstream observation, not a blocker attributed to the group refactor.

This run's normal released-baseline cleanup also required a newly inspected same-state retry after an initial nested-child 409 on group deletion. Independent checks verified all nine captured consumer objects and the separate setup RG absent, with both states empty. No casing workaround, added ignore, state edit or broad RG recovery deletion was used. These results do not establish candidate teardown or fresh example E2E success.

Normal released-baseline teardown removed the VM, disk, NIC, reservation, Reader and network. The first group deletion returned a nested-child 409 after child deletion; independent absence/empty-group readbacks preceded a newly inspected same-state normal destroy retry. The retry and separate empty setup-RG teardown succeeded. This is **recovered cleanup**, not an unconditional first-attempt destroy pass or candidate teardown proof. Protected exact-source evidence retains both rejected plans and the failed/recovered cleanup. This example is not claimed to have passed fresh E2E or VM migration.
